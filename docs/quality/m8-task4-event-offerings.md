# M8 Task 4: read-only event registration availability

The Events Calendar owns the published event schedule and canonical event page. In the disposable stack, ORAS Tickets 0.4.60 owns public registration: `_oras_tickets_v1` and `_oras_tickets_woo_map_v1` associate an event with WooCommerce-backed ticket products, while `_oras_rsvp_v1` configures that event's RSVP. Event Tickets and Event Tickets Plus are not installed there. ORAS AI resolves an event through its TEC connector before passing only that resolved event ID to ORAS Tickets.

For paid tickets, ORAS AI reads `Event_Offering_Resolver::resolve_for_event()`, which evaluates the sale window and current Woo product stock and purchasability. For RSVP, it reads `RSVP_Capacity::state()`, whose decision includes public and Registration Desk admitted counts. These are local database-backed reads at request time; ORAS AI does not cache a positive registration state. An on-sale selectable ticket or RSVP `admit` yields `open`; sold-out stock or a full RSVP yields `full`; a closed/not-yet-open sale or RSVP window yields `closed`; missing providers, associations, malformed or mixed non-open states yield `unknown`. An open sibling offering can establish event-level open state even if another offering is full or fails. No ticket, product, attendee, order, or RSVP record is passed to the answer model.

The handoff URL is the TEC canonical page for the exact selected event, checked by ORAS AI's HTTPS host allowlist. A distinct provider URL cannot replace it. Without a qualified link, the assistant makes no positive registration recommendation. The answer guard uses current `event:<subject>:registration` facts and never treats schedule alone as availability. Generic upcoming-event questions inspect at most the ten TEC candidates returned by the existing query and select the earliest qualified open event; if none is open, they report the earliest event's bounded state without recommending registration. Questions such as "this event" or "where can I register?" without a resolvable event identity request the event name and do not query an arbitrary offering.

Disposable `tests-cli` qualification used TEC 6.17.3.1, ORAS Tickets 0.4.60, and WooCommerce 11.1.0. Native read APIs returned `on_sale/available/selectable` for a stocked test product, `on_sale/sold_out/not selectable` for zero stock, `open/admit` and `closed/refuse` for RSVP windows, no tickets for an unconfigured event, and `unavailable` for a ticket without its Woo mapping. A direct run of the ORAS AI connector against a TEC ORM-created test event and linked Woo product returned `open`, `full`, `closed`, and `unknown` as the product and association changed. The probes deleted all test events and products, and the temporary copy of connector files was removed. The local site's private HTTP URL cannot qualify a production HTTPS handoff; the production plugin was not activated in that wp-env. Answer integration is covered by repository tests. Production event mappings, installed versions, live capacity, and canonical HTTPS links still require verification before deployment.
